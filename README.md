# ZAGATOVKY — витрина заготовок

Витрина кулинарных заготовок (Алматы) и админ-кабинет к ней. Клиент собирает корзину,
оформляет заявку и продолжает разговор в WhatsApp или Telegram — онлайн-оплаты нет.

## Что где лежит

```
ZAGATOVKY/                     ← этот репозиторий = ФРОНТЕНД
├── src/                       витрина (React 19 + Vite + Tailwind v4 + GSAP)
├── admin/                     админ-кабинет, отдельное приложение и отдельный деплой
├── e2e/                       Playwright: витрина и кабинет
├── docs/DESIGN.md             дизайн-система (источник правды по цветам и типографике)
└── backend/                   ← БУДУЩИЙ ОТДЕЛЬНЫЙ РЕПОЗИТОРИЙ (API + БД)
```

Три независимых проекта со своими `package.json`. Пакетный менеджер — **pnpm** (версия
зафиксирована в `packageManager`, так что локально и в Docker ставится одно и то же).

## Быстрый старт

```bash
# 1. База и API
cd backend
cp .env.example .env
docker compose up -d          # Postgres на порту 5433
pnpm install
pnpm db:migrate               # применить схему
pnpm db:seed                  # 10 заготовок, 2 набора, категории, владелец
pnpm dev                      # http://localhost:3000  (Swagger: /docs)

# 2. Витрина
cd ..
cp .env.example .env
pnpm install
pnpm dev                      # http://localhost:5173

# 3. Кабинет
cd admin
cp .env.example .env
pnpm install
pnpm dev                      # http://localhost:5174
```

Учётка владельца после сида: `owner@zagatovky.kz` / `zagatovky123` — **смените пароль
перед выкладкой в прод** (Кабинет → Команда → Пароль).

## Проверка

```bash
pnpm typecheck                # витрина
cd admin && pnpm typecheck    # кабинет
cd backend && pnpm typecheck  # API

pnpm e2e                      # весь набор Playwright (нужны все три сервиса)
pnpm e2e:smoke                # только безопасные проверки, можно по проду
```

`e2e/admin.spec.ts` создаёт и удаляет данные — гоняйте его только по дев-стеку.
Заказы, созданные тестами, помечаются `isTest` и не попадают ни в основной список
заявок, ни в статистику кабинета.

## Типы API

Фронтенды не описывают ответы сервера руками: `src/types/api.ts` генерируется из
OpenAPI-схемы работающего API и коммитится в репозиторий.

```bash
pnpm gen:types                             # с локального API
API_SCHEMA_URL=https://<api>/docs/json pnpm gen:types
```

Если бэкенд поменяет форму ответа, ошибка вылезет на тайпчеке, а не у клиента.

## Деплой (Railway)

Четыре сервиса: `postgres`, `api`, `storefront`, `admin`.

| Сервис | Откуда собирается | Порт |
|---|---|---|
| api | репозиторий бэкенда, `backend/Dockerfile` | 3000 |
| storefront | этот репозиторий, корневой `Dockerfile` | 8080 |
| admin | этот репозиторий, root directory `admin` | 8080 |

Переменные фронтендов (**build-time** — Vite вшивает их в бандл на этапе сборки):

```
VITE_API_BASE_URL="https://<api>.up.railway.app/api/v1"
VITE_MEDIA_BASE_URL="https://<публичный домен R2>"
```

Переменные бэкенда описаны в `backend/README.md`. Миграции применяются
контейнером на старте — отдельный шаг деплоя не нужен.

## Как разнести на два репозитория

Структура для этого уже готова: между корнем и `backend/` нет ни одного импорта,
общего lockfile тоже нет.

1. **Бэкенд.** Скопируйте папку `backend/` в новый репозиторий как его корень.
   Внутри уже лежат свои `.gitignore`, `.env.example`, `docker-compose.yml`,
   `Dockerfile` и `README.md` — папка самодостаточна.
2. **Фронтенд.** В этом репозитории удалите `backend/`. Витрина и `admin/` остаются
   вместе: это два фронтенда, которые деплоятся разными сервисами из одного репо.
3. Свяжите их переменными окружения из таблицы выше — захардкоженных адресов в коде нет.

Проверить разделимость можно, не разнося ничего по-настоящему: скопируйте `backend/`
во временную папку и соберите там, затем соберите корень и `admin/` при отсутствующей
папке `backend/`.
